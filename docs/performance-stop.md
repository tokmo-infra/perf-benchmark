# 可选停测与诊断

多轮闭环可显式设置 `scheduler.settings.stop_on_underfill: true`；默认关闭。要求 standard
maxtpm、完整选中数据的有限首遍、单 Trial、无重试和主动取消场景。起点使用与标准 maxtpm
相同的显式百分比或自动解析值；当前不支持零百分比。仅当原始客户端 in-flight 事实及最终
Turn 完成时间共同证明起点后连续低于目标 60 秒时请求停测，随后对账 native 窗口。触发后
通过 Run 的共享取消令牌停止当前 Trial 并结束 Run。

未返回的原生请求可能已有更早的完成时间，不能用墙钟替代其完成事实。等待证明没有任意
超时：可能一直等到自然结束；真正的交接错误、无效栅栏或无法安全保存的回放使控制器
HOLD，不自动停测。预派发请求的完成下界可在事件循环内安全推进；已提交请求不能这样处理。
指标与持久化队列确认均在取消前完成，对账未通过时诊断标记结果存在风险。

`PERF_TTFT_LIMIT_MS` 为正整数时启用原生首个文本输出 watchdog；计时从连接池获取后
发起传输开始，不包含客户端排队；即使响应头尚未到达，已发送请求超过限时也会取消当前 Trial
的原生请求并结束 Run。此时状态未知，不能推测服务端后来是否会返回 500。已观察到 HTTP 500
时保留 500 事实，不把迟缓正文或事后超限判定改记为 watchdog；但 500 仍可能与独立的欠并发
停测同时发生。未设置、无效或非正数
时 watchdog 关闭；非文本和非流式负载不应使用此文本输出保护。可选的 `PERF_CONTROL_DIR`
须为已存在的绝对目录；其中的一次性 `native-stop.json` 和 `safety-stop.json` 为通知而非
权威结果，目录应由调用方为每个 Trial 独立管理，I/O 错误会报告失败。

完成队列诊断按 native 窗口报告首遍成功请求的 TTFT、TPOT、decode 样本覆盖和缺失原因，
并按 typed Attempt 计数 HTTP 500 和未知状态，不改变窗口公式或推测缺失 token、样本与成功。
取消期间已返回的真实 Attempt 仍可靠交接，Turn 可以保持 cancelled。

**客户端 in-flight 或已发送并发不是服务端正在执行的 P+D 请求数。** 如需验证实际 P+D
达到目标，须独立采集并对齐服务端执行、排队和 tokenization 等观测；不得仅凭客户端并发、
停测规则或 CPU 回归推断服务瓶颈、模型吞吐或 SLO。
